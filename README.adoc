== Introduction

The **Dynamic Discovery Client (DDC)** is a library designed to **look-up** and **retrieve** based on resource/participant and subresource/document metadata identifiers from the publisher server (e.g. Service Metadata Publishers (SMP) servers.

The  library is composed out of several components acting together to execute the task:
The **Publisher Locator component** is designed to determine the publisher address based on resource identifiers. This lookup can be executed using DNS or through a preconfigured key-value dictionary.
The **Document Request Provider component** constructs the requests necessary for fetching the documents, while the **Document Fetcher component** is responsible for retrieving these documents from the publisher server.
Following retrieval, the **Document Reader component** parses the documents and extracts the data into a common target object. The Document Reader supports various document types (e.g., OASIS SMP 1.0, OASIS SMP 2.0) and standardizes the data extraction process into common final objects, which are then utilized by the user application. This seamless support for multiple document types eliminates the need for modifying application code when adding the support of the new Document type.
The requests and document parsing logic are implemented within **the extensions**, enabling custom document support.



=== Purpose of this document

This page provides a brief description of how to use this DDC to connect to a Service Metadata Publisher using CNAME or NAPTR record to find out and retrieve Receiver Recipient Metadata.

== Setting up parameters

The DynamicDiscoveryBuilder class provides 6 interfaces and theirs default implementations, however, the user is free to use customized implementations to fit other needs.


=== Interfaces and implementations

**IPublisherLocator**

This interface is responsible for managing the lookup algorithm and providing the URL or URI for the request. By default it provides the implementation **eu.europa.ec.dynamicdiscovery.core.locator.impl.DefaultBDXRLocator** for looking up NAPTR or CNAME records. The lookup  returns the first result(s) found for each top domain and DNS record type (for the same top domain and NAPTR record type, multiple results can be returned with different NAPTR services).
The method returns just the first successful result, thus it does not iterate over all possible options to optimize performance by reducing the number of lookup queries!

Alternative is the **eu.europa.ec.dynamicdiscovery.core.fetcher.impl.StaticMapMetadataLocator.** for preconfigured/default SMP URI.

**IDNSLookup**

This interface is responsible for executing the DNS queries. The default implementation is  **eu.europa.ec.dynamicdiscovery.core.locator.dns.impl.DefaultDNSLookup** which is based on https://github.com/dnsjava/dnsjava[DNSJava
library].

**IDocumentFetcher**

This interface is responsible for fetching the response from the request. By default it provides the implementation **eu.europa.ec.dynamicdiscovery.core.fetcher.impl.DefaultURLFetcher.**

**IDocumentRequestProvider**

This interface is responsible for building the REST URL for fetching the target document.
As input, it uses the resource/participant identifier and the SMP results from the locator. The builder builds the URL for fetching the resource/subresource (e.g. SMP  ServiceGroup/ServiceMetadata) document from the located SMP.
The DDC library is shipped with the default it provides the implementation supporting the eDelivery SMP 1.0 and eDelivery SMP 2.0 standards for building the request URL.

**eu.europa.ec.dynamicdiscovery.core.provider.impl.DefaultDocumentRequestBuilder.**

**IDocumentReader**

This interface is responsible for parsing the response according to the **IExtensions**. By default, it uses the implementation **eu.europa.ec.dynamicdiscovery.core.reader.impl.DefaultBDXRReader.** with supporting the Oasis SMP 1.0 and  Oasis SMP 2.0 extensions.

**IExtensions**

This interface contains a list of **IObjectReader** for the extension. The purpose of the implementation is to provide necessary methods for DDC client to ready various document and to produce standard internal SMP objects.  By default, DDC contains

* **eu.europa.ec.dynamicdiscovery.core.extension.impl.OasisSMP10Extension** implementation of the Oasis SMP 1.0 standard
* **eu.europa.ec.dynamicdiscovery.core.extension.impl.OasisSMP20Extension** implementation of the Oasis SMP 2.0 standard

**IObjectReader**

Reads the (XML) Document and generates the Target (SMPServiceGroup or SMPServiceMetadata) output object.

**ISignatureValidator**

This interface is responsible for verifying the signature of the response according to the XSD and is used by the abstract class **eu.europa.ec.dynamicdiscovery.core.security.AbstractSignatureValidator**, all the implementations must extend this abstract class.
The default  implementation **eu.europa.ec.dynamicdiscovery.core.security.impl.DefaultSignatureValidator** is provided.

=== Discovery process

The discovery process starts with the configuration of the Lookup rules. If custom Lookup configuration is not provided, the default configuration is built from the extension provided data (1). The next step is the Lookup of the publisher address (2). The lookup follows the rules defined in the configuration. When first successful result is found the lookup stops and discovery process continues. The result can contain multiple URLs with various services (e.g. lookup with NAPTR DNS records: Meta:SMP, oasis-bdxr-2). If the publisher address is not found  the process is stopped and the error is thrown (3).
In the next step, the extension for fetching and parsing is set. The order of the extensions is defined by the DDC configuration (e.g first Extension Oasis SMP 2.0 is set and then fallback with Oasis SMP 1.0). In case there is no next extension the error the discovery of the data ends with error (5).

The process continues with building of list of the requests (6). The request(s) are build using the
resource/participant (optionally: subresource/document) identifier and the publisher address results from the locator. The list of requests is built according to the extension configuration (e.g first:Meta:SMP, oasis-bdxr-2 and then "any" service ). In case there is no next request, then the next extension is set and the process continues with building the request(s) for the next extension.

The next step (7) is to fetch the data from the publisher request. The fetcher is fetching the data
from the publisher until it finds first successful responses.

The response is then parsed (8) by the reader. The reader is using the extensions to parse the response and generate the target object (e.g. SMPServiceGroup or SMPServiceMetadata).

1. The client calls the **getServiceGroup** method of the DynamicDiscovery class to retrieve the SMP ServiceGroup document data for the participant. Alternatively, the **getServiceMetadata** method can be called to retrieve the SMP ServiceMetadata document data for the participant and target document.
2. The lookup method of the **IPublisherLocator**  implementation returns the list of SMP URLs (List of Lookup Results). The provided implementations are: the static **StaticMapMetadataLocator** to return preconfigured list of SMPs URL or the **DefaultBDXRLocator** to lookup the DNS entries for the participant identifier.
3. The DynamicDiscoveryService class calls the **buildRequest** method of the **IDocumentRequestProvider** implementation to build the REST URLs for fetching the resource/participant document from the located SMP.
4. The DynamicDiscoveryService class calls the **fetchData** method of the **IDocumentFetcher** implementation to retrive document bytearray from the "REST" URL.
5. The DynamicDiscoveryService class calls the **parseData** method of the **IDocumentReader** implementation and returns target object e.g. SMPServiceGroup or SMPServiceMetadata which is used by the client to get the data
6. The DynamicDiscoveryService class returns the data to the client.

=== Locator configuration

The DDC has two  Locator implementations.
- **DefaultBDXRLocator** lookup's the authoritative domain DNS given as a constructor parameter.
- **StaticMapMetadataLocator** returns SMP's  URI based on preconfigured party identifier and URI mapping. If the party identifier is not found in the mapping, it returns the default URI.

==== BDXL DNS Locator configuration (DefaultBDXRLocator)

The DefaultBDXRLocator used the **new DefaultBDXRLocator.Builder()** for configuration with the following options:

- **topDnsDomains**: Ordered List of top DNS domains to be used for lookup.  The client will use the first domain in the list that contains the DNS record for the participant to proceed with further processing (fetching the document).
- **dnsLookupTypeList**: Ordered List of DNS lookup types (NAPTR, CNAME) to be used for DNS lookup.
- **dnsLookup**: DNS lookup implementation. The implementation performs the DNS lookup. If not provided the  **DefaultDNSLookup** is used.
- **resourceSchemeMandatory**: (default is false) If true, the client will throw an exception if the resource/participant identifier scheme is not found in the resource/participant identifier.
. **resourceWildcardEnabled**: (default is false). If true, the client will use the wildcard domain for lookup the resource/participant identifier. For details see the document "Software Architecture Document"  bdmsl_allowed_wildcard.
- **resourceSchemeValidationPattern**: (default is null) The client will validate the resource/participant identifier scheme against the provided pattern. If the pattern is not matched, the client will throw an exception.
- **resourceCaseSensitiveSchemas**: (default is empty list) The list of resource/participant identifier schemes that are case-sensitive. if the resource identifier is not case-sensitive it will set it to lower case when calculating the hash for DNS lookup query.
- **resourceFormatterTypes**: The list of resource/participant identifier formatter types. The client will format/normalize the resource/participant identifier before lookup according to the formatter type. By default, ebCoreParty Identifier type and Peppol Party identifier types are registered.
- **cnameURLScheme**: (default is http) The client will use URL scheme when resolving SMPs URL using the CNAME DNS records.
- **cnameURLContextPath**: (default is '/') The client will use the context path when resolving SMPs URL using the CNAME DNS records.

=== Proxy configuration

By default **eu.europa.ec.dynamicdiscovery.core.fetcher.impl.DefaultURLFetcher** does not use proxy configuration. In order to use proxy, an instance of the class **eu.europa.ec.dynamicdiscovery.core.security.impl.DefaultProxy** must be configured and passed by parameter as follows:

Example:
[source,java]
----
DynamicDiscovery smpClient = DynamicDiscoveryBuilder.newInstance().fetcher(new DefaultURLFetcher(new DefaultProxy("127.0.0.1", 8000, "user", "password"))).build();
----

=== Signature Truststore configuration

In order to check if the certificate extracted from the signed response is trusted even if the signature is valid, a truststore must be passed by parameter to the Signature Validator implementation.A trusted certificate must be included in the truststore.

Example:
[source,java]
----
 KeyStore truststore = KeyStore.getInstance("JKS");
 truststore.load(new FileInputStream(Thread.currentThread().getContextClassLoader().getResource("example/truststore.ts").getFile()), null);

 DefaultSignatureValidator signatureValidator = new DefaultSignatureValidator(truststore);
----

=== Configure regular expression to validate signature certificate subject

Apart from validating response of signer certificates against the truststore, the Dynamic Discovery gives the possibility to add (optional) a regular expression to validate any certificate metadata related to the subject of the signer certificate.

In order to add this optional validation, please follow the steps below:
[source,java]
----
// Default Signature Validator with regex to check certificate subject

KeyStore truststore = KeyStore.getInstance("JKS");
truststore.load(new FileInputStream(Thread.currentThread().getContextClassLoader().getResource("example/truststore.ts").getFile()), null);

String regexSubjectValidation = "^CN=eDelivery_SMP_TEST_1.*$"
DefaultSignatureValidator signatureValidator = new DefaultSignatureValidator(truststore,regexSubjectValidation);

// Default Signature Validator

KeyStore truststore = KeyStore.getInstance("JKS");
truststore.load(new FileInputStream(Thread.currentThread().getContextClassLoader().getResource("example/truststore.ts").getFile()), null);

DefaultSignatureValidator signatureValidator = new DefaultSignatureValidator(truststore);
----

=== Configure Default Fetcher HTTPS with mutual TLS authentication and allowed algorithms

Following example configures the default fetcher with allowed TLS Cipher suites and TLS versions.
The cipher suits names and TLS versions are supported and defined by JCE provider or JAVA version standard names:

https://docs.oracle.com/en/java/javase/18/docs/specs/security/standard-names.html#sslcontext-algorithms

[source,java]
----
KeyStore clientKeystore = CommonUtil.loadKeystore("/truststore/server-keystore.p12", KEYSTORE_TYPE, PASSWD);
KeyStore clientTruststore = CommonUtil.loadKeystore("/truststore/tls-truststore.p12", KEYSTORE_TYPE, PASSWD);

DefaultURLFetcher testInstance = new DefaultURLFetcher.Builder()
        .enableHttpScheme(false)
        .tlsKeystore(clientKeystore, PASSWD.toCharArray())
        .tlsTruststore(clientTruststore)
        .tlsCipherSuites("TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA256", "TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384")
        .tlsVersions("TLSv1.2","TLSv1.3")
        .build();
----

== How to use the dynamic discovery client

The DynamicDiscoveryBuilder is responsible for creating a new instance of the Dynamic Discovery Client. By default, there are implementations for all core services provided by the tool however new customized implementations can be used by the user.

Default implementation example:
[source,java]
----
KeyStore truststore = KeyStore.getInstance("JKS");
truststore.load(new FileInputStream(Thread.currentThread().getContextClassLoader().getResource("example/truststore.ts").getFile()), null);

DynamicDiscovery smpClient = DynamicDiscoveryBuilder.newInstance()
.locator(new DefaultBDXRLocator("ehealth.acc.edelivery.tech.ec.europa.eu"))
.reader(new DefaultBDXRReader(new DefaultSignatureValidator(truststore)))
.build();

ParticipantIdentifier participantIdentifier = new ParticipantIdentifier("9925:0367302178", "iso6523-actorid-upis");
----

=== Get list of service group documents

SMPServiceGroup serviceGroup = smpClient.getServiceGroup(participantIdentifier);

SMPServiceMetadata serviceMetadata = smpClient.getServiceMetadata(participantIdentifier, new SMPDocumentIdentifier("urn::epsos:services== epsos-21", "epsos-docid-qns"));

=== Certificate Pinning/Whitelisting: A Security Technique for Validating Digital Certificates

A SMP Certificate Pinning/whitelisting is a security mechanism that integrates into dynamic discovery infrastructure,
validating expected digital certificates against predetermined service parameters (e.g., participant identifiers,
document identifiers). This service enables dynamic receiver to whitelist/pinned certificates, ensuring that only registered
certificates can participate in secure message exchange.

[source,java]
----

   X509Certificate certificateToValidate = ... ;
   String expecteDertificateCode = null;
   try {
        smpClient.certificateExists(certificateToValidate, expecteDertificateCode,
                resourceIdentifier, subresourceIdentifier,
                processIdentifierIdentifier, transportProfile);
    } catch (DDCCertificateNotFoundException e) {
        LOG.error("Certificate in not trusted for given parameters!", e);
    } catch (TechnicalException e) {
        LOG.error("The certificate can not be validated!", e);
    }
----
